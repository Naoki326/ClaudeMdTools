# 链接地址由服务配置 host 推导，不无条件用局域网 IP

`/lanbook` 命令与启动横幅要回答同一个问题：**该给用户哪个地址？** 早期 pi 扩展自己探测局域网 IPv4 生成链接，完全忽略 `settings.json` 的 `host`——于是 `host: 127.0.0.1` 时仍输出 `http://100.114.42.112:30142/...`，而服务根本没绑那张网卡，链接必然打不开。这是把「服务配置」与「展示地址」当成两件不相干的事导致的。

现在两者共用 `lib/link-host.js` 一份推导规则：

| 服务配置 host | 链接地址 | 理由 |
|---|---|---|
| `127.0.0.1` / `::1` / `localhost` | `127.0.0.1`，并标记 `loopback` | 服务只绑回环，局域网 IP 必然连不通；上层据此提示用户 |
| 具体网卡地址 | 该地址 | 唯一可达入口，不猜网卡 |
| `0.0.0.0` / `::`（默认） | 探测到的局域网 IPv4 | 通配监听时任何本机地址都可达 |

探测局域网地址时按「真实私网优先」排序：`192.168/16` > `10/8` > `172.16/12` > Tailscale CGNAT `100.64/10` > 其它。`os.networkInterfaces()` 的枚举顺序不保证，装了 Tailscale 的机器上 `100.x` 会排在 Wi-Fi 私网地址前面，生成的链接对普通手机不可达。虚拟网卡（VMware / WSL / Docker / Hyper-V）仅在没有任何真实网卡时才使用——此时不谎报 `loopback`，否则用户会以为服务没监听局域网。

## Considered Options

- **按 host 推导（选定）**——地址与服务实际监听行为一致，一条规则覆盖回环/网卡/通配三种配置
- 永远给局域网 IP——host 收敛到回环时产出打不开的链接（本次修复的 bug）
- 永远给 127.0.0.1——跨设备场景（主场景）失效
- 让用户手工配置展示用地址——多一个要维护的字段，且默认值仍会错

## Consequences

- 扩展不得自己实现 host/端口解析；`lib/link-host.js` 是唯一真相（测试守护：扩展源码不得出现本地 host 语义分支）
- 扩展随包分发，需 `createRequire` 加载这个 CJS 模块（相对路径在仓库与安装后都成立）
- 服务端启动横幅继续按自己的逻辑列出所有可达地址（它可以列多条）；`link-host` 只解决「给用户一条能点开的链接」
